# UC Topup Store

A responsive storefront for in-game items: UC top-ups, suits and car skins.

- **Shop:** category tabs, search, rarity and sort filters, product details, cart drawer (desktop) and sticky cart bar (phone), light and dark themes
- **Checkout:** multi-item orders priced on the server, paid from the user's wallet, idempotent (a retried submit can't charge twice)
- **Fulfilment:** each line is delivered on its own. A failed line is refunded on its own, and the order shows `delivered`, `partially_refunded` or `refunded`
- **Accounts:** sign up, log in, log out, profile, saved PUBG Player ID, password change (bcrypt, httpOnly JWT cookie, rate-limited auth)
- **Orders:** order list, order detail with progress timeline, per-item status and delivery reference, printable receipt
- **Wallet:** balance, activity history, demo top-ups (development only)

Stack: Node.js + Express 5, Postgres (Neon in production, embedded PGlite locally), vanilla JS/CSS. No build step.

## Quick start

```bash
npm install
npm start          # http://localhost:3000
npm test           # 19 API tests against an isolated temporary database
```

Unless `NODE_ENV=production` is set, the defaults are `PAYMENT_MODE=demo` and `DELIVERY_MODE=simulate`. That means **nothing is actually delivered and top-ups are free**. This is fine for trying the site and must not be used for a live store.

## Local database

Without `DATABASE_URL`, the app runs an embedded Postgres (PGlite) stored in `data/pgdata`. Delete that folder to reset local data. The schema and sample catalog are created automatically on first start.

Upgrading from the SQLite build? Delete `data/app.db*` once. The new schema lives in `data/pgdata`.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3000` | HTTP port |
| `NODE_ENV` | — | Set to `production` for live deployments (enables safety checks) |
| `JWT_SECRET` | random (dev only) | **Required in production.** A long random string |
| `DATABASE_URL` | — | Postgres connection string. **Required in production** (use the Neon pooled URL). Unset locally means embedded Postgres |
| `PGLITE_DIR` | `data/pgdata` | Folder for the embedded database when `DATABASE_URL` is unset |
| `PG_POOL_MAX` | `3` | Connection pool size. Keep it low for serverless |
| `PGSSL` | TLS on | Set to `disable` only for a local Postgres without TLS |
| `BRAND_NAME` | `UC Topup` | Shown in the header, footer and page title |
| `CURRENCY` | `USD` | ISO currency code for display |
| `PAYMENT_MODE` | `demo` (dev) / `gateway` (prod) | `demo` credits top-ups instantly. `gateway` returns 501 until a provider is wired in |
| `DELIVERY_MODE` | `simulate` (dev) / unset (prod) | Dev and test values: `simulate`, `fail`, `fail-cosmetic`. In production an unset value means every line is refunded |

The server refuses to start in production if `PAYMENT_MODE=demo`, a dev-only `DELIVERY_MODE` is set, or `JWT_SECRET` is missing.

## How checkout works

1. The client sends `{ items: [{ product_id, quantity }], pubg_id, client_ref }`. It never sends prices.
2. The server looks up each active product and computes the total. It rejects a cosmetic bought with quantity > 1, more than 10 lines, or quantities over 10.
3. In one atomic transaction the server checks the balance, creates the order and its lines, and debits the wallet.
4. Each line is handed to `fulfil()` in `delivery.js`. Results are recorded per line.
5. Failed lines are refunded in one transaction, and the order status is set.

`client_ref` is a per-attempt id generated by the browser. Submitting the same reference again returns the original order with `duplicate: true` and charges nothing.

## Catalog

Categories and products live in the database. The sample data in `seed.js` is a placeholder. Edit it or change rows in the `products` table.

- A category's `fulfilment` decides which delivery channel handles its lines: `uc` or `cosmetic`.
- `popular` adds the badge. `active = 0` hides a product and blocks purchases of it.
- Rarity is one of `common`, `rare`, `epic`, `legendary`.

The placeholder names (for example "Frostline Suit") are generic. They are not real PUBG item names. Replace them with items you are authorized to sell.

## Deployment: Neon + Vercel

Neon holds the data and Vercel runs the app. The Express app runs as one serverless function, and `public/` is served from Vercel's CDN.

1. **Neon.** Create a project. Copy the **pooled** connection string (host contains `-pooler`).
2. **Vercel.** Import this repository as a project. Framework: *Other*. Vercel reads `vercel.json`.
3. **Environment variables** (Production):

   | Name | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon pooled connection string (mark as *Sensitive*) |
   | `JWT_SECRET` | Output of `openssl rand -hex 32` (mark as *Sensitive*) |
   | `NODE_ENV` | `production` |
   | `PAYMENT_MODE` | `gateway` (keeps top-ups off until a provider is connected) |
   | `BRAND_NAME`, `CURRENCY`, `PG_POOL_MAX` | Optional |

   Leave `DELIVERY_MODE` unset. In production every order line is then refunded, so nothing is given away.
4. **Deployment protection.** Turn off *Vercel Authentication* (SSO protection) under the project's settings. Otherwise only team members can open the store.
5. Deploy. The first request creates the tables and loads the sample catalog.

The app refuses to start in production without `DATABASE_URL` or `JWT_SECRET`, and refuses demo payments or simulated delivery.

## What you must finish before going live

The app is a complete foundation. Three pieces are placeholders on purpose:

1. **UC delivery** (`delivery.js`, branch `uc`). Connect an official top-up channel or an authorized reseller/supplier API.
2. **Suit and car-skin delivery** (`delivery.js`, branch `cosmetic`). Only sell these if the publisher authorizes a delivery channel for them. Without one, every cosmetic line is refunded, which is the intended production behavior.
3. **Payments**. Wire a provider (for example Stripe or Razorpay) into `POST /api/wallet/topup`. Verify webhook signatures and credit the wallet only after the provider confirms payment. Never trust the client's amount.

Also recommended before launch:

- **Player ID verification.** Confirm the account exists and show the nickname before charging.
- **Reconciliation.** Lines left in `processing` after a crash between charging and delivery need a job that retries or refunds them.
- HTTPS (the session cookie is `Secure` in production) and a reverse proxy in front of Node.
- Terms of service, refund policy, privacy policy and contact details. None are included.
- Neon backups and point-in-time restore settings for the production branch.
- An admin area for managing products and viewing orders. Not built yet.
